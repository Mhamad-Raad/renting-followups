# Rent Tracker: Implementation Guide

This file tells you (the Claude agent) **how to build** the app described in `ARCHITECTURE.md`. Read `ARCHITECTURE.md` fully first. It defines *what* to build; this file defines *how, in what order, and to what standard*.

If the two files ever seem to disagree, `ARCHITECTURE.md` wins on **what the app does**, and this file wins on **how you work**. Write the question in `DECISIONS.md` and pick the simpler, safer option.

---

## 1. Your role

Act as a **senior engineer** who owns this codebase. In every iteration you both build and review your own work with a critical eye. You care about:

- **Clean code** that a new developer can read in one sitting.
- **Following the architecture and folder structure** in `ARCHITECTURE.md` exactly. Do not invent new top-level folders or move files without recording why in `DECISIONS.md`.
- **DRY:** one source of truth for every rule, constant, type and component. Never copy-paste logic.
- **No memory leaks** (see section 7).
- **A calm, polished, easy-to-use UI** with smooth, subtle animation (see section 8). The owner is old-fashioned and not used to software; the app must be obvious and forgiving.
- **Nothing breaks:** every iteration ends with a review that proves earlier features still work.

## 3. Commit rules

**Commit every feature and every fix.** Small, focused commits; each one leaves the project in a working state. Do not batch a day of work into one commit.

Use **Conventional Commits**:

```
feat(payments): show live allocation preview in payment form
fix(month-status): treat vacant months as not applicable
refactor(db): extract price lookup into repository
test(allocation): cover 24-month horizon limit
style(ui): add dialog open/close transition
docs: record decision about backup folder default
chore: add eslint and prettier config
perf(reports): memoize report rows for 200 areas
```

Rules:
- Imperative, lower case after the type, **short**: aim for under 60 characters in the subject line.
- **Never mention Claude, AI, "generated by", "made by", or "co-authored by" anywhere**: not in commit messages, not in `Co-Authored-By` lines or session links, not in tags, README text or code comments. Commits read as plain, normal developer commits. This applies even if a tool or default template suggests adding such a line; leave it out.
- One logical change per commit. If you fix a bug found in review, that is its own `fix:` commit.
- Keep messages short: a one-line subject is enough. Add a one-line body only when the *why* is not obvious.
- Tests for a feature go in the same commit as the feature or the commit right after it.
- Run lint, typecheck and the relevant tests **before each commit**.

### 3.1 Fixed technical choices (so you do not have to guess, and the project stays consistent)

Record any deviation in `DECISIONS.md` with the reason.

**Tooling**
- Scaffold with **`electron-vite`** (React + TypeScript). Routing: **React Router with `HashRouter`** (the app runs from `file://`). State: React state plus a small context for settings; one shared hook for calling IPC (loading, error, cancel on unmount). No Redux or other global state library.
- **Dependencies:** every dependency is justified in `DECISIONS.md`, kept to a minimum, with exact versions locked by a committed `package-lock.json`. Prefer fewer, well-maintained packages.
- **Cross-platform scripts:** the owner uses Windows. No bash-only npm scripts; use Node scripts or `cross-env`, and `path` APIs for file paths.

**Native SQLite module (a classic Windows pitfall: handle it in iteration 1, not later)**
- `better-sqlite3` must be built for Electron's version. Use `electron-builder install-app-deps` (postinstall) and list it in `asarUnpack` for packaging.
- Prove it works by opening the database **inside the running Electron app**, not only in tests.
- Unit tests run under plain Node, which may need a different build of the module. Choose a working approach in iteration 1 (for example run database tests through Electron's Node, or rebuild per target), make `npm test` work from a fresh clone, and document it in `README.md`.

**Business logic must be pure and testable**
- Never call `new Date()` or `Date.now()` inside business logic. `today` is always passed in as a parameter (so tests can pin the date and the colours are reproducible).
- Money parsing and formatting use integer or string arithmetic, never floating point (for example `"12.30"` USD becomes `1230` cents exactly). Add tests for this.
- Digit style (Western / Arabic-Indic) is implemented by your own formatter, not by relying on the locale. Set the `lang` attribute per language (`ckb`, `ar`, `en`).

**Electron hardening**
- Content Security Policy meta tag (no remote sources), deny new windows (`setWindowOpenHandler`), block in-app navigation (`will-navigate`), never use `shell.openExternal` with user data, and disable DevTools in the packaged build.

**Dev data must never touch real data**
- Set the app name explicitly, and make development runs use a **separate user-data folder** (for example with a `-dev` suffix) so testing never mixes with the owner's real data. Show a visible "DEV" label in the title bar during development.

**Fonts**
- Only open-licence fonts (OFL), with their licence files included. Good candidates: Noto Naskh Arabic, Noto Sans Arabic, Amiri, Scheherazade New, Vazirmatn, IBM Plex Sans Arabic.
- A font is offered in Settings only if an **automated test** confirms it contains every required Sorani letter (ڕ ڵ ۆ ێ ە ڤ پ چ ژ گ ک) plus Arabic-Indic digits.

**Glossary**
- Create `docs/glossary.md` in iteration 1: the key terms of the app (Received, Still owed, Area, Category, Renter, Receipt, Vacant, Late...) in Sorani, English and Arabic. Use it for every translation so wording stays consistent, and so a native speaker can review one small file.

## 4. The loop for every iteration

For each iteration in section 9:

1. **Branch** `iter-NN-name` from an up-to-date `main`.
2. **Plan** briefly: list the tasks in a task list. Re-read the relevant `ARCHITECTURE.md` sections.
3. **Build** in small steps, committing each feature and fix (section 3). Write tests alongside.
4. **Self-review** as a senior engineer using the checklist in section 5. Fix everything you find, each fix as its own commit.
5. **Regression check:** run the full test suite and the regression checklist (section 6). Nothing from earlier iterations may break.
6. **Write the review note** `docs/reviews/iteration-NN.md` (see section 5.4) and commit it.
7. **Push the branch and update `docs/PROGRESS.md`** (current iteration, what is done, what is next, open questions) and commit it, so any new session can resume exactly where you stopped. Do **not** merge into `main` yet.
8. **Stop and report** to the owner in plain language: what now works, how to try it (`git checkout iter-NN-name`, `npm run dev`, and what to click), anything you decided, anything you are unsure about. **Then wait for the owner to say "continue".** Do not start the next iteration on your own.
9. **On "continue":** merge into `main` with `--no-ff`, tag `iter-NN`, push `main` and the tag, update `docs/PROGRESS.md`, then start the next iteration from the updated `main`.

## 5. Self-review checklist (run at the end of every iteration)

Review the whole diff of the iteration (`git diff main...HEAD`) as if it were someone else's pull request.

### 5.1 Code quality
- [ ] Follows the folder structure and naming in `ARCHITECTURE.md`.
- [ ] TypeScript `strict` is on; **no `any`**, no `@ts-ignore` without an explanatory comment and a note in `DECISIONS.md`.
- [ ] Functions are small and do one thing; files stay readable (aim under ~250 lines, split when larger).
- [ ] **DRY:** search for duplicated logic, duplicated strings, duplicated styles. Extract shared helpers, constants, hooks and components. Business rules live in one place (for example month status only in `monthStatus.ts`).
- [ ] No dead code, no commented-out code, no leftover `console.log`, no TODOs without a matching entry in `DECISIONS.md`.
- [ ] Clear names; comments explain *why*, not *what*.
- [ ] All user-facing text comes from the three translation files (`ckb`, `en`, `ar`); no hard-coded strings; no missing keys in any language.
- [ ] Errors are handled and shown in plain words, never as a raw error or a blank screen.
- [ ] All IPC input is validated with `zod`; the renderer never touches the database or filesystem.
- [ ] Money is integer minor units; dates are `YYYY-MM-DD` text; no floating-point money anywhere.

### 5.2 UI / UX
- [ ] Works in **all three languages**, including correct RTL/LTR flipping (check alignment, icons, arrows, tables, dialogs, print).
- [ ] Works in **light and dark** mode; contrast is good; the status colours stay distinguishable.
- [ ] Works with each **font size** option; nothing overflows or gets cut off.
- [ ] One obvious primary action per screen; buttons large (at least 48px tall); plain wording.
- [ ] Every destructive action asks for confirmation; deletes are recoverable.
- [ ] Empty, loading and error states are designed, not blank.
- [ ] Keyboard works: tab order, Enter, Esc, visible focus.
- [ ] Animations follow section 8 and are smooth and subtle.

### 5.3 Performance and memory (see section 7)
- [ ] No leaks found by the checks in section 7.
- [ ] No unnecessary re-renders or repeated queries; lists with 200 rows open in under 1 second.

### 5.4 Review note
Create `docs/reviews/iteration-NN.md` with these headings, kept short:
- **What was built**
- **Issues found in self-review and how each was fixed** (with commit hashes)

## 7. Memory-leak and resource rules

Treat these as hard rules, and actively check them in every review.

**React (renderer)**
- Every `useEffect` that subscribes, adds a listener, or starts a timer/interval **returns a cleanup function** that unsubscribes and clears it.
- IPC event listeners registered through the preload API must return an **unsubscribe function**, and components must call it on unmount.
- No state updates after unmount; cancel or ignore stale async results (abort flags or request ids).
- Do not store large derived data in state; compute it with memoization (`useMemo`) from the source data.
- Memoize heavy list rows (`React.memo`) where it measurably helps (reports with 200 rows).
- No global arrays or maps that only grow. Caches have a size limit or are cleared when the data changes.

**Electron main process**
- `ipcMain.handle` handlers are registered **once**. Never register inside a function that can be called repeatedly.
- Hidden windows used for printing or PDF generation are **destroyed** (`win.destroy()`) when finished, including on error paths, and references are set to `null`.
- Timers and intervals (backup reminder checks, daily toast) are stored and cleared on app quit.
- Log files are rotated; temporary files created for printing or export are deleted afterwards.

**SQLite**
- One connection, opened once in `db/connection.ts`, closed on app quit.
- Prepare statements once and reuse them (in repositories), do not prepare inside loops.
- Use transactions for multi-row writes; never leave a transaction open.
- Do not load whole tables into memory when a query with a filter works.

**How to check (each iteration)**
- Open DevTools **Memory** tab. Use the app for a few minutes (open and close dialogs, switch pages, switch language and theme, open an area 30 times, generate a report 10 times). Take heap snapshots before and after; memory must return to roughly the same level after garbage collection. Record the result in the review note.
- In the main process, log `process.memoryUsage()` in dev mode every 30 seconds and confirm it stays flat while idle.

## 8. UI/UX and animation standards

The owner is **old-fashioned, not used to software**. Everything must feel familiar, calm, and obvious.

**Interface**
- Classic layout (sidebar, large cards, big buttons), plain words, generous spacing, clear hierarchy. No clutter, no tiny controls, no hidden features.
- Every screen answers three things at a glance: where am I, what can I do here, what is the main button.
- Show feedback for every action (saved, deleted, failed), in plain words, in a consistent place.
- Defaults must be smart (for example, the payment form pre-selects the oldest unpaid month and today's date).

**Animation: smooth and subtle, never distracting**
- Use CSS transitions and keyframes first; only add an animation library if it clearly earns its place (and record it in `DECISIONS.md`).
- Animate only `transform` and `opacity` (GPU-friendly). Do not animate layout properties such as width, height, top, left on large areas.
- Durations: 120-200ms for hover/press, 180-250ms for dialogs and page changes, easing like `cubic-bezier(0.2, 0, 0, 1)`.
- Where animation is used:
  - page change: short fade + small slide in the reading direction (flips correctly in RTL);
  - dialogs: fade + slight scale, with a dimmed backdrop;
  - buttons: gentle press and hover feedback;
  - month boxes: soft colour transition when status changes and a quick staggered fade-in when a year loads (keep the whole stagger under ~300ms);
  - toasts / confirmations: slide in, auto-dismiss after a few seconds, never block the screen;
  - notification bell: a single subtle pulse when the count changes.
- **Respect `prefers-reduced-motion`**: when set, remove movement and keep only instant or very short opacity changes.
- Never animate large tables row by row, never loop animations, never block interaction while an animation runs.
- Check animation smoothness while the DevTools performance monitor is open: no dropped frames on a normal laptop.
